## One architecture, distinct applications

```text
                            [AETHERION SERVER]
       FastAPI HTTP | canonical SQLite | provenance | care events
            |                |                  |
   Windows Qt Desktop    Android companion    Wear OS companion
     (prototype)             (planned)          (planned)

   Reference library: NASA science + licensed verified medical content
   Optional AI gateway: LOCAL / CLOUD (not a safety-critical authority)
```

### Server

`apps/server/` is a separate executable process. It handles subject- and source-identity, typed observations, timestamps, quality, scope, time-series queries, scientific references, incident events and a persisted care journey. Medical rules require clinically reviewed evidence. Future local/cloud AI cannot override deterministic alert/identity logic. For any public or multi-device deployment, access control and privacy measures must be built and verified first.

### Native Windows application

`apps/desktop/` is **not** a browser, a WebEngine wrapper, or a localhost website. It is a PySide6/Qt interface with a **persistent top horizontal navigation** and product content beneath. Opening the application immediately shows a useful Mission Control surface, **not** a splash, setup wizard or fake login before the main menu.

**Major views and intended interactions:**

| Screen | Essential visible behavior |
|---|---|
| Mission Control | Crew cards, valid source status, last time, scope-aware environment panel, real trend points, clear technical/health event split |
| Personal Health / Today | Healthy-person first, no required symptom intake, available/missing/old measurements, sleep/activity/wellbeing distinguished |
| Body Atlas | True 3D camera/mesh picking when offered, accessible 2D fallback explicitly labelled, science/data layers and exact organ selection |
| NASA Explore | Five distinct hazards: radiation, isolation, distance, gravity, hostile/closed habitat; every causal claim has a primary source |
| My Journey / Care | GATHER → EVALUATE → ACT → RECHECK on one person/episode with real persistence and human review |
| Guide + Encyclopedia | Source-linked, searchable material usable without LLM; 119 conditions only if full authentic source catalog is actually verified |
| Assistance | User/witness report, acknowledgement, care follow-up and trustworthy delivery status; no claims of unconsciousness from silence |

**Visual system:** restrained aerospace/medical look; legible type, informative sparklines/charts, genuine state changes, scientific source drilldowns, keyboard access and tested 100/150% DPI. Dark palette is acceptable but appearance is secondary to working navigation and provenance. Do not build a mock-only UI to claim completion.

### Genuine 3D acceptance

A 3D-labelled feature requires mesh geometry, perspective/orthographic depth-buffered camera, orbit >=180°, pan, zoom, reset, ray pick and stable anatomical IDs connected to reference data. Evaluate **PyVistaQt/VTK** versus **VisPy** in Windows native Qt (Q-0121), test both candidates, select **one** adapter, audit mesh/asset licenses, record FPS and Windows package impact. SVG/video/animated image is a 2D fallback, never a 3D PASS.

### Source integrity and clinical safety

- Observation must declare `subject_id, scope, metric, value, unit, observed_at, received_at, source_id, quality, verification_state`; test fixtures are not patient telemetry.
- Missing, stale, invalid, unavailable, not authorized and reported values have different semantics. No-data ≠ healthy.
- A lost heartbeat/check-in ≠ detected unconsciousness; separate technical alerts, user reports and verified medical issues.
- NASA Open Science Data Repository (OSDR) may contain research datasets, not live streams. A NASA citation or a file called `119` does not prove 119 authentic complete NASA records.
- Data imported from the previous ASTRA repository is **not automatically approved**. Maintain verifiable author/publisher URI/version/hash and redistribution license status.
- The initial local API lacks production-grade authentication; no patient, real private health or clinical use may be claimed.

### Six intended integrated journeys

A. Daily health → Mission & Personal show the same actual recorded values and history.  
B. NASA gravity source → Atlas system selection → matching measurements or accurate NO_DATA.  
C. Optional symptom report → evidence-limited evaluation → ACT → RECHECK → restart and recover.  
D. Witness report → one incident → ACK → matching crew Care, no fictional dispatch.  
E. Internet/cloud AI unavailable → local documented functions continue, unsupported functions fail closed.  
F. Watch integration when genuinely implemented → typed device event → source-aware server receipt → selected view and ACK. **Scenario F remains future/blocked until a real client exists.**

## Hackathon scope versus long-term ambitions

**Now (P0):** prove Server+native Windows UI, actual persisted observations, source-linked NASA evidence, at least one meaningful care journey, tests, honest demo and official submission. A smaller working and provable implementation is preferable to 300 declared-but-empty features.

**Enhancements (P1):** broad five-hazard exploration, richer true 3D, accessible UX, audited 119-condition reading and integrated assistance, if evidence can be collected.

**Post-hackathon (P2):** independently installed mobile/watch, actual devices, optional local/cloud AI, clinical and privacy validation, richer release packaging.

**Research horizon (P3, 2027–2050):** public-health adoption on Earth, remote healthcare settings, extreme environment validation and possible Mars-oriented crew autonomy. **2050 is a design aspiration; not a NASA-confirmed mission schedule.**

## Repo and ownership boundaries

`apps/server/`, `apps/desktop/`, `apps/mobile/`, `apps/watch/`, `packages/contracts/`, `knowledge/`, `tests/`, `submission/`, `docs/`, `scripts/` are the canonical areas. Do not fork into a second app because a task is blocked. Work in exact files claimed through 300 individual Quest records.

### Pass/fail evidence

No feature passes from code presence alone. Require actual unit + API + SQLite restart tests, real native Windows interaction, no dead controls, traceable provenance, asset redistribution audit, and if a feature is advertised as 3D a real ray-pick mesh demonstration. The official NASA submission must be independently accessible and reproducible.
